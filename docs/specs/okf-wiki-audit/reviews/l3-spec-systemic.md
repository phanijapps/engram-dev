# Review — OKF 0.2 spec + wiki-contract machinery (adversarial, LEVEL 3)

> Fresh-context read-only reviewer (run 1de0bd90), 2026-10-07, repo @ HEAD 660ac42+.
> Scope: OKF_SPEC_v0.2.md as normative document; implemented wiki contract
> (freshness stamp, findings ledger, managed markers, summaries); U1–U6 plan
> drift. Unedited reviewer output; parent synthesis in ../gap-1.md.

1. **[major] Spec contradicts its own versioning rule.** Evidence: §12 "a **minor** version bump introduces backward-compatible additions" vs §13 "v0.2 supersedes OKF v0.1 and is a minor version bump under §12, except for two deliberate **breaking changes**." Why: the minor/major rule is the compat contract every consumer (incl. this repo's 0.1 validator eating a 0.2 bundle) keys off; the spec's own precedent legitimizes incompatible minors. Close: amend §12 with an explicit flagged-breaking-change exception or bump major upstream.
2. **[major] The toolchain declares 0.2 but validates 0.1 — U1 is not started in kit.** Evidence: `engine/okf/okf_kit/core/validate.py:32` `_SUPPORTED_OKF_VERSION="0.1"`; cli.py:42 "OKF v0.1"; templates.py:29 default "0.1"; `engine/okf/tests/fixtures/wiki/index.md` declares `'0.1'` though AGENTS.md calls it "the OKF 0.2 migration fixture"; only `memex_core/knowledge.py:20` (`OKF_VERSION="0.2"`) writes 0.2. `memex-core status` on this repo's own wiki permanently reports `okf-version-mismatch`. Close: land U1.1–U1.8 or stop writing 0.2 in wiki_init.
3. **[major] Generator writes v0.1 idioms into the 0.2-declared bundle.** Evidence: `engine/okf/okf_kit/code/render.py:135-137` emits a body `# Citations` list (the exact thing §13.1 supersedes with frontmatter `sources`); generated concepts carry no `generated: {by,at}` (U1.1) and no `sources` family (U1.3) — provenance lives in private keys `source_path`/`source_hash`. Declared version and content dialect disagree. Close: render 0.2 families (actor per §7, hash as a source signal); validator warns on legacy `# Citations`.
4. **[major] Freshness stamp is blind to the working tree and to indexer config.** Evidence: `engine/core/src/memex_core/resolve.py:112-114` — freshness = `stamp.repo_head == git HEAD` only; uncommitted source edits keep the wiki "fresh" (the normal agent state); `knowledge.py` stamp records no profile/scope, so re-indexing with different include/exclude on the same commit stays "fresh". Close: stamp a dirty-tree flag or input fingerprint + profile/scope; resolve reports "dirty"/"scope-changed".
5. **[major] Findings ledger has no supersession/reopen — keys are terminal forever.** Evidence: `engine/core/src/memex_core/findings.py:113-118`: any existing finding at `(source,destination,kind)` is returned as-is; after accept, a genuinely new proposal with new rationale is silently swallowed (same hole as declined, minus the flag). Close: allow supersede-on-accept (new id chaining prior) and an explicit reopen verb for declined-with-new-evidence.
6. **[major] Resolution records no actor and no rationale.** Evidence: cli.py:88-90 `resolve <id> --decision` only; `Finding` (findings.py:34-42) has no `resolved_by`/note field. Why: violates the repo's own "configured authority accepts" discipline and OKF §7's actor convention — the ledger can't answer *who* accepted a normative page or why. Close: require `--by` (§7 syntax) + optional note; add field.
7. **[major] Destination lifecycle is unvalidated.** Evidence: propose takes free-string destination (no existence/path check, findings.py:103-132); rename/move of the destination page orphans accepted findings and a re-propose under the new path yields a duplicate id; nothing ties an accepted finding to the content it authorized (no applied-digest), so accept-then-rewrite is indistinguishable from accept-as-written. Close: validate/normalize destination within `wiki/`, re-key or supersede on rename, record post-acceptance digest.
8. **[minor] No conflict handling; `kind` is unregulated free text.** Evidence: two pending findings at one destination with different kinds coexist silently; no kind vocabulary exists (CLI passes any string, cli.py:86) so dedupe is evadable by synonym. Close: kind enum + per-destination pending/conflict count surfaced in resolve/status.
9. **[minor] `list_findings` docstring lies about ordering.** Evidence: "oldest first" (findings.py:152) but `_dump` sorts `(kind, id)` (findings.py:130) and id is a truncated sha1 — effectively hash-random chronology. Close: sort by `proposed_at` (id tiebreak) or fix docstring.
10. **[minor] Concept identity is under-specified and kit cites a dead spec section.** Evidence: §2 Concept ID = path minus `.md`; nothing on case sensitivity (macOS/Windows collisions), hidden dirs (`.okf/` — resolve.py:88 invents the exclusion), symlinks; meanwhile validate.py:91-93 cites "the SPEC §2.2 segment regex" which does not exist in the vendored 0.2 doc (0.1-era dangling reference). Close: spec defines ID syntax + hidden-dir rule; kit message cites its own regex.
11. **[minor] No concept supersession/redirect or move semantics.** Evidence: §5.4 has `deprecated` but no `superseded_by`; §6.1 recommends absolute links as "stable when documents are moved within their subdirectory" — silent on cross-directory moves; dangling links are MUST-tolerate with no repair lifecycle. Renames, the norm in git, are unaddressed. Close: add a supersession/alias path convention and a link-rewrite rule kit's graph can honor.
12. **[minor] Sub-bundles cannot declare a version.** Evidence: §12 permits frontmatter only in the bundle-root `index.md`, while §3 allows a bundle to be "a subdirectory within a larger repository"; kit invented forward-compat for exactly this hole (validate.py:96-101 "nested-index-frontmatter … possible sub-bundle marker"). Close: spec defines nested `okf_version` semantics or a manifest alternative.
13. **[minor] Resolution base for path-valued frontmatter fields is undefined.** Evidence: §6.2 accepts "a relative path (for example `../computations/revenue.md`)" but never states the base for `computation`/`executor.resource`/`attester.resource` (links define theirs; frontmatter doesn't). Two conforming consumers can resolve differently — fatal for attestation comparison. Close: one sentence — relative frontmatter paths resolve against the concept file.
14. **[minor] No bundle identity — federation (U6) has no namespace.** Evidence: no bundle name/URI anywhere in the spec; absolute `/tables/orders.md` from two bundles collide when merged; kit's private `repo` key on generated concepts (render.py:52) is the de-facto patch. Close: optional `bundle_id` root key + namespaced link resolution.
15. **[minor] The wiki's private machinery has no discoverable profile.** Evidence: `.okf/` state dir (findings.toml, last-index.json), `<!-- okf-code:start/end -->` managed regions, keys `managed_by`/`source_path`/`source_hash`/`generated_profile`/`summary_level`/`package`/`area` — all legal under §4.1 extensions but ungoverned: no `x-`-style namespacing, no superspec a bundle consumer can find; OKF 0.3 defining a colliding key (`sources` was already taken this way) is undetectable since §11 MUST-NOT-reject. Extending *inside* 0.2 is honest only with a declared profile. Close: author "memex profile of OKF 0.2" (bundle-consumable, e.g. `.okf/PROFILE.md`)) + prefix private keys.
16. **[minor] Managed body regions are spec-invisible and one hand-edit bricks wiki_update.** Evidence: §4.2 body is freeform; legally editing a generated page (removing markers) makes `_preflight_existing_concepts` abort the entire index run — indexer.py:211-218 "refusing to index over existing non-okf-code concept" — with no repair verb in memex-core. Close: document the managed-region contract in-bundle and add an adopt/repair op.
17. **[minor] Spec is silent on the security surface every consumer inherits.** Evidence: no YAML limits/alias guidance (kit privately adds an 8MiB cap, parse.py:22, and uses `safe_load`), no injection guidance for HTML renderers though kit ships a web graph view, and `resource`/`sources[].resource` are arbitrary URIs a naive consumer may fetch. Close: spec sets expectations (safe YAML subset, URIs opaque); kit web sanitizes.
18. **[minor] U1–U6 scorecard drift: much of the plan is paper.** Evidence: U2 fingerprints — zero code (`grep fingerprints` = 0 hits in engine/; `.okf/` holds only findings+stamp); U3 — findings real but in engine/core, not kit as plan §D assigns, and `bindingness` has zero hits repo-wide; U4 — compile_context.py is real (manifest, CONTEXT_INSUFFICIENT) but is keyword federated search, not relations+provenance mandatory closure; U5 UI inbox — absent from engine/okf/web; U6 — partial (search.py federation; no consolidation→findings). Close: mark each U-row done/partial/paper in the plan.
19. **[nit] Version mismatch is invisible in `status`.** Evidence: status.py:52-58 reports only error/warning/info *counts*; the perpetual `okf-version-mismatch` info is indistinguishable from 500 routine `extension-key` infos. Close: echo top info codes.
20. **[nit] Flagship wiki index defeats progressive disclosure.** Evidence: wiki/index.md = frontmatter + `# memex_beta`, zero §8 sections; no index.md under code/, code-summaries/, domain/, decisions/, systems/; kit's `regenerate_indexes` exists but `wiki_update` (knowledge.py) calls only `index_codebase`. Close: wire index regen into wiki_update or state the curated-intent.

**Verdict:** The OKF 0.2 spec is a good minimal core undermined by one self-contradiction (breaking changes under a minor bump) and by systemic gaps any bundle ecosystem hits: no supersession/move semantics, no bundle identity, no path-resolution base, no security posture. The repo's wiki contract is honest-but-undocumented 0.2 extension — the real blockers are drift: kit still validates/authors 0.1 while memex-core declares 0.2, freshness ignores the working tree, and the findings ledger can't supersede, attribute, or survive renames. Land U1 for real, write the profile, harden the ledger — then the private extensions are defensible.
